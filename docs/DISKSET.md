# The Apple Pascal 1.3 disk set

What every file is for, and how much of it has been reconstructed. The
descriptions in the first section are the user's, kept verbatim. The status
column and the second section are this repo's.

The machine-readable companion is `analysis/diskset-inventory.txt`,
regenerated by `tools/diskmap.py` on every build: every file on the three
1.3 evidence disks with its per-segment breakdown -- dictionary slot, segment
number, SEGINFO version, mtype, size, and how many procedures are p-code and
how many are native 6502. That file is generated and this one is not; where
they disagree, the generated one is right.

**The target is 1.3 and the 128K system only** (`128K.APPLE` +
`128K.PASCAL`). The 64K `SYSTEM.APPLE`/`SYSTEM.PASCAL` and all of 1.1 are
archived -- see **Archived** at the end. The core rows below name the 128K
files; the descriptions are still the user's, verbatim.

| 128K.APPLE | Boot files that configure the Apple hardware. | **reconstructed -- all 16,384 bytes identical to shipped** (finding 279): the 128K interpreter as three `.ABSOLUTE` assemblies (`src/native/interp/`, generated by `tools/absdis.py` from `128K.hints`), assembled by `SYSTEM.ASSMBLER` and joined by `MAKEINTP` on the 1.3 system. | 128K.PASCAL | The main operating system and command menu. | **22469 of 23040 bytes: the whole file but three slack tails that were another tool's memory** (finding 284): Apple's compiler on `PASCALSYSTEM.text`, finished by `MAKEOS` on the 1.3 system, which splits segment 0 as the 128K boot loads it (283). `probe_128k_pascal.py`. **Earlier: all 111 procedures instruction-, jump- and frame-identical in ONE compile of Apple's compiler** (finding 280): a program-level `USES FIOPRIMS` through the include `USESFIO.TEXT` ends finding 232b's two-run trade. All 58 segment-0 procedures are byte-identical to Apple's two pieces, every `SEGKIND` is Apple's (`FIOPRIMS` is `INTRINSIC CODE 2` with `(*$NS 3*)`), and slots 2-6 carry Apple's slack (282). Segment by segment: `PASCALSY` 57/58, `GETCMD` 27/27, `INITIALI` 11/11, `PRINTERR` 1/1, `USERPROG` 1/1, `FILEPROC` 8/8, `FIOPRIMS` 5/5. `FIOPRIMS` is now written as the `UNIT` its `SEGKIND` says it is, declared inline and `USES`d with no library round trip (finding 232). The one procedure left in that run is `FGET`, and finding 232b shows it **cannot** be reached in a single compilation of a single file: its `USES` would empty `PROCTABLE[2..5]` after `EXECERROR`'s body had filled slot 2, and its own completion cannot move earlier because its nested `EXECGETCH` must claim procedure 56. `FGET` is written and verified all the same, in a second kept run that trades those four for it (finding 233) -- so **all 111 procedures have been produced byte-for-byte by Apple's own compiler**, and `probe_os_exact.py` checks the union of the two runs is 111. That claim briefly stood at 108: making jump destinations part of the comparison (finding 252) showed `PASCALSY.2`, `.33` and `.55` each send one jump to the wrong instruction while emitting Apple's instructions in Apple's order, and finding 253 fixed all three first attempt -- `EXECERROR` had the CONTROL-RESET hang on the inner `IF`'s `ELSE` rather than the outer one's, `SCANTITLE` assigned its result inside an `ELSE` so a plain title returned `FALSE`, and `BLKXFER` left one statement outside a `THEN`. The count is 111 again and now rests on a comparison that can see control flow. The `FGET` run is derived from the live source by `tools/fgetvariant.py` rather than kept as a snapshot, so a fix to a procedure both runs contain lands in both. The shipped dictionary says the same thing from the other side -- `SEGKIND` 6 with `TEXTADDR` 0, and a slot 15 no compile writes -- so `128K.PASCAL` was not produced by one compile. The narrative below is the history and is not kept current.** Target is 128K.PASCAL specifically (`src/pascal/os/1.3/PASCALSYSTEM.text`, findings 136-148); 7 segments, 105-111 procedures depending on build. The skeleton compiles clean under Apple's own `SYSTEM.COMPILER` first attempt: `CONST`/`TYPE`/`VAR` ported from UCSD II.0's `GLOBALS.TEXT`, its own 41 forward-declared segment-0 procedures (27 "fixed", 14 "non-fixed"), and all 7 segments in their real disk slots. `USERPROG` (segment 1) and `PRINTERR` (segment 3, `params=4/data=46`, Apple reworded its messages and added 128K ProFile-specific error codes) are both frame-exact, straight from UCSD's own source once written as direct `FWRITELN`/`FWRITESTRING` calls (`WRITE`/`WRITELN`'s own sugar only accepts a plain variable, not a pointer dereference, on Apple's real compiler). `SCONCAT`/`SINSERT`/`SCOPY`/`SDELETE`/`SPOS` (segment 0, what `CONCAT`/`INSERT`/`COPY`/`DELETE`/`POS` sugar lowers to) are all five exact too -- Apple's real parameter *order* for these diverges from UCSD's own literal text, recovered by reading each body's own algorithm directly, not assumed (finding 138). `FGOTOXY` is close (`params=4/data=0` against real `4/2`, one documented word -- Apple's own body caches a pointer this one re-derives instead, finding 140). 42 of segment 0's 43 procedures now match Apple's real `params` exactly. `PASCALSY`'s own 451-word global `VAR` section -- what nearly every other remaining procedure depends on -- is started (263 of 451 words currently declared): the real `SYSCOMREC` type, and `SYSCOM` (offset 1) plus `GFILES[1]` (offset 3, the real target of every segment-0 body's own console-output call) confirmed by reading `FGOTOXY`'s own real body directly (finding 139). `MAXUNIT` corrected from UCSD II.0's own `12` (1.1's value) to `20` (1.2/1.3's, per Neil Parker's documented `DISKNUM` table, finding 141), widening `UNITABLE` by 48 words. `MAX_SEG` also corrected, 31 -> 63 (same Parker annotation, finding 142) -- widens `SYSCOMREC.SEGTABLE`, a heap structure reached through the `SYSCOM` pointer, so it does not move `PASCALSY.1`'s own frame at all (confirmed inert, both compilers agree). **The 451-word `VAR` section is now closed exactly** (finding 143): Parker's document transcribes every field Apple added past UCSD II.0's own globals (Dave Tribby's reverse-engineered names, `CONFIG_CHAR` through `WHAT_L`), self-consistent against this file's own word-size formulas with zero exceptions across ~26 fields; procedure 1 now compiles to `params=0/data=902`, an **exact match** to Apple's real `128K.PASCAL`, on both the host compiler and Apple's own. Field boundaries are verified by the frame-size match; individual field identities (beyond `SYSCOM`/`GFILES[1]`) remain STRONG INFERENCE. `PASCALSY.1`'s own main-loop body is started (finding 144): `EMPTYHEAP := NIL`, `UNITCLEAR(1)`, `INITIALIZE` written and verified exact. `FINIT`/`FCLOSE` now resolved (finding 145): the mystery file variable is `EXEC_FILE: FILE`, an untyped 40-word file collapsing seven of finding 143's own Tribby-guessed fields -- Apple's own compiler auto-generates both calls from the `VAR` declaration alone, confirmed byte-for-byte. Procedures 44-47 (findings 146/147) -- the EXEC-file buffered I/O layer -- now written and verified exact too. Procedure 50 (`WAITSYSVOL`, finding 148) is now written as well -- `params=0` exact, `data` documented one word short (likely tied to an unresolved `GFILES[1]^`-addressing question); `48`/`49` are declared as number-preserving stubs only, since reaching `PASCALSY.58` (which `48`'s own real loop calls) needs `51`-`57` declared first, six of which are lexically nested one level inside a not-yet-identified enclosing procedure -- real, separate work. That nested-scope group resolved into four independent pairs by caller-graph analysis (finding 149); the `G<n>`/`FIB` labeling trap in the lift for `lex 0` segment-0 procedures' own frames was found and corrected (finding 150), cross-corroborated against `SYSTEM.LIBRARY`'s own `PASCALIO.text` (finding 151), which also confirmed the Tribby/`MAXUNIT`/`MAX_SEG` changes stay inert there by design (same finding). `PASCALSY.51`/`52` (the `"S#/P#/I#"` and `"Execution error #"` diagnostic printers nested inside `EXECERROR`) and `EXECERROR` itself (`PASCALSY.2`, whole body) are now written for real and VERIFIED BINARY FACT, read from `128K.PASCAL`'s own raw p-code directly rather than the lift's abstracted rendering (findings 153/154) -- disassembling instruction-for-instruction identical to the real binary apart from two flagged, expected fast-tier compiler-codegen differences. Still stubs: `EXECCLOSE`, `SPACEWAIT`, `FETCHDIR`'s own real bodies, `PRINTERROR`'s real per-code message table, and `PASCALSY.1`'s own main `REPEAT ... UNTIL EMPTYHEAP = NIL` loop (which calls `PASCALSY.48`, also still a stub), along with every other forward-declared procedure's real content and four of the six other segments' content beyond procedure 1. `FINIT`/`FEOF`/`FEOLN` written for real (finding 155); `FILEPROC`'s real six-word shared dispatch signature discovered and its arm-1/2/3/4/7 routing written, unblocking `FRESET`/`FOPEN`/`FCLOSE` as real forwarders (findings 156-157, a new parameter-clause-reversal rule found along the way). `FBLOCKIO`'s nested chunked-transfer loop (`PASCALSY.55`, written as `BLKXFER`) matches the real binary instruction-for-instruction; `FBLOCKIO`'s own outer body and its file-extension helper `STUB49` are both now written whole too (findings 158-165), resolving `FIB`/`DIRENTRY`'s real packed-field offsets by probe (twice correcting a hand-counted first guess) and a `CBP`/`CGP` call's own result-reservation convention along the way -- both compile clean but, unlike `BLKXFER`, could not be verified instruction-for-instruction due to a fast-tier quirk where the host compiler omits them from their own procedure table for reasons not tracked down; labelled STRONG INFERENCE pending the acceptance tier. Still stubs: `FILEPROC`'s own arm bodies (2/3/4/7), `FGET`/`FPUT` and the rest of the `FIB` read/write layer, the whole `FIOPRIMS` segment, `SPACEWAIT`/`FETCHDIR`'s real bodies, `PRINTERROR`'s real per-code message table, and `PASCALSY.1`'s own main loop |

## Also on the disks

The list above is the interesting half. The disks carry more:

* **`LINEFEED.CODE`** (APPLE3) -- suppresses line feeds. One procedure, 38
  bytes, and **reconstructed** (finding 99a).
* **`SYSTEM.CHARSET`** (APPLE1) -- the hi-res character set, 1024 bytes.
  **Reconstructed**, identical, written by `MAKECHRS` from
  `src/data/CHARSET.TEXT` on the 1.3 system (finding 278).
* **`SYSTEM.SYNTAX`** (APPLE1) -- the compiler's error messages. Already a
  text file on the disk, so it is reproduced by writing the volume.
* **`II40.MISCINFO`, `II80.MISCINFO`, `HAZEL.MISCINFO`** (APPLE3) -- the
  terminal profiles SETUP writes. Every setting and the zero tail
  reproduced by Apple's SETUP from recipes, 370, 396 and 361 of 512
  bytes; the rest is memory SETUP never writes (finding 277).
* **Eleven `.TEXT` sample programs** (APPLE3) -- `BALANCED`, `CROSSREF`,
  `DISKIO`, `GRAFCHARS`, `GRAFDEMO`, `HILBERT`, `SPIRODEMO`, `TREE`,
  `HAZELGOTO`. Already source on the disk. (Their 1.1 `.CODE` twins, once
  the lifter's calibration corpus, are archived with 1.1.)

## What is left, by size

Counting procedures rather than bytes, and 1.3 only: 216 done of roughly
861. Every remaining target can be read before it is written: the sweep
covers the codefiles the three 1.3 disks carry, and every one lifts with
the stack fully tracked (finding 100 counted 1147 of 1147 when the 1.1
copies were still swept). The listings are in `analysis/utilities/`, p-code and
pseudo-Pascal side by side.

## Archived

Not targets, not read by the build, kept verbatim:

* **The 64K system** -- `SYSTEM.APPLE` and `SYSTEM.PASCAL` on the 1.3
  `APPLE1` image. They cannot leave that image without modifying evidence,
  so `disasm_utils.py`/`lift_utils.py` and `probe_split_segment.py` skip
  them by name. Their generated listings are in `archive/analysis/`.
* **Apple Pascal 1.1** -- the `APPLE2` image and the two UCSD 1.1 images,
  moved byte for byte to `evidence/archive/1.1/`; the 1.1 compiler source
  in `archive/src/pascal/1.1/`; every 1.1-only or 1.1-vs-1.3 tool and probe
  in `archive/tools/`; and the generated 1.1 analysis in
  `archive/analysis/`. See `archive/README.md`.
